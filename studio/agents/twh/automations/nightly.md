# 夜间巡检

每天定时、无人值守地核对功能地图：地图说的和源码一致吗，和真实界面一致吗。地图漂了改地图，功能坏了只报告，不改产品代码。流程照 pstack 的 `maintain-verification-skill`，结果三选一：`clean`、`changed`、`blocked`。

## 运行环境

- 不在主工作树里跑。`pnpm twh worktree new nightly-<日期>` 从最新的 origin/main 建一个干净的 worktree。上一次的 nightly worktree 先 `pnpm twh worktree audit`，已合并且干净的 `prune` 掉。
- 只启动自己 `pnpm twh launch --build` 的匿名实例。结束必须 `pnpm twh cleanup`，并确认没有留下进程和端口。
- 需要 `pnpm build`，第一次会慢。

## 流程

1. **索引卫生。** 读 `.agents/skills/verify-twh/features/README.md`，对照目录里的文件和 `studio/verification/features.json`，补上缺的、删掉多的。运行 `node scripts/check-feature-map.mjs`。
2. **源码核对。** 每个功能文件派一个只读子 Agent（`Explore`），从源码回答"这个用户可见的功能怎么工作"：入口有哪些、可能的漂移在哪（带文件和行号）、给一条实跑配方。子 Agent 不驱动应用、不改文件。
3. **汇总。** 把重叠的实跑配方并成尽量少的几个应用状态。抽查被标为漂移的地方；说是干净的不用重证。翻最近的提交，找有没有用户可见的新界面还没进地图，要有具体的源码路径才算。
4. **实跑。** 即使源码看起来没问题也要跑。`launch`，`doctor`，然后逐个功能按它文件里的命令驱动一遍。全程守住三条：
   - 驱动前体检；一次驱动失败之后，再驱动前重新体检或重启，不要带着问题硬跑。
   - 证据在清理之后仍然在它该在的位置，去看一眼，不要假设。
   - 驱动留下的东西不过夜：失败的尝试留下的残留也要清掉。
5. **分诊。**
   - 地图写的和用户看到的路径不一致：地图漂了，改地图。
   - 功能是好的，但驾驭命令驱动不了：工具缺口，修 `scripts/twh/`，修完重新实跑。
   - 应用真的坏了：产品回归，记下来给操作者，不写进这次的提交。
6. **收尾。** `changed` 时把修正单独提交（只动验证 skill 自己的目录和 `scripts/twh/`），按 `land-on-main.md` 走裁判后推 main。`clean` 或 `blocked` 不提交，如实报告覆盖到哪里。
7. **抽查当天的裁决书。** 列出 `studio/.runtime/judge/` 里今天的裁决书。对每一份，用 `ReadSession` 找到登记它的那次运行，确认裁判是另一个上下文、说明文件里的证据确实存在。对不上的写进汇报的第一行。裁决书是自报的，这是唯一的防伪手段。

## 汇报

一句话说结果，然后列出：覆盖了几个功能、哪些够不到（缺什么前置条件、走的哪条路）、确认的漂移、发现的产品回归、裁决书抽查的结果。产品回归和对不上的裁决书放在最前面。
