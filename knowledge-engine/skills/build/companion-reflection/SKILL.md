# 构建：近况回信

检索相关旧线索时依赖 [common-retrieval](../../common/retrieval/SKILL.md)，只扩展能实质改变本次理解的来源；本文保留中性证据卡、人物视角与朋友式回信流程，不套用预测检索预算。

这个 Skill 负责 `wiki/12 近况对话/` 的朋友式回信。共享人物库和主辅推理契约只由 `knowledge-engine/skills/common/reasoning-lenses/SKILL.md` 维护；本 Skill 负责来源选择、朋友身份、成文、归档和总览。

## 使用边界

- 用户明确要求回信、朋友式回应或长者式回应时使用。
- 宽泛摄取只有在 `companion=update` 时使用。
- 来源没有具体经历、想法、关系时刻或值得回应的原句时返回 `no-op`。
- 它不替代状态追踪、个人主线、人物页或心理诊断。

Studio 的导入后冷启构建属于宽泛摄取：若一批材料包含具体个人经历、想法或关系时刻，从最新或最能代表本批变化的一篇来源中选择一篇标记 `companion=update`，生成或更新一封回信。不要为批次中的每个文件机械写信；只有整批都缺少可回应的个人材料时才 `no-op`，并在矩阵摘要里说明证据理由。历史来源的回信回到来源当时的处境，不伪装成今天的近况。

## 先读

1. 完整读取用户指定的日记或来源。
2. 新建或更新归档回信时读取 `wiki/12 近况对话/近况对话总览.md`；独立人物视角版本跳过此步。
3. 按线索读取真正改变本次理解的主线、阶段、循环、系统、人物、事件或状态页，关键旧判断追溯原始来源。若中心涉及变化，核对变化前的具体处境；不为了少读而把有来路的变化写成当天偶然的感想，也不为显得了解用户堆砌旧事。
4. 读取 `knowledge-engine/skills/common/reasoning-lenses/SKILL.md`；证据核验按其中的护栏引用执行。
5. 运行 `python3 knowledge-engine/skills/common/reasoning-lenses/scripts/list_lenses.py`，选择主视角后只读取对应人物文件；辅助人物同样按需读取。
6. 读取 `references/friend-voice.md`。

## 独立人物视角版本

Studio 的「用新视角重读」只借用所选回信的日期、主题和来源元数据定位材料，原回信页面 ID 只用于保存版本。写信过程不得读取原回信正文、近况对话总览或其他已生成版本，也不得从它们取得中心判断、结构或措辞。若元数据不足以定位具体原始来源，说明缺口并停止；不要通过阅读旧信补齐。

此模式从原始材料重新建立中性证据卡，完整读取用户选择的人物文件，沿其推理起点、路径、洞见标准和停止位置独立写一封信。无需与旧回信比较或查重。结果只作为派生版本由 Studio 保存，不修改 Wiki 文件、总览或日志。

## 归档和日期

- 总览：`wiki/12 近况对话/近况对话总览.md`
- 单篇：`wiki/12 近况对话/YYYY-MM-DD 标题.md`
- 日期取来源日期；一篇日记对应一封信。已有回信时更新原页，不建立重复页面。
- 总览或目录不存在时，随第一封回信创建最小可用总览，不因知识库刚建立而跳过。

## 工作流

1. 执行共享视角工作流，使用强度 3：从中性证据卡到选角、视角任务卡和候选洞见。完整读取所选人物及其校准案例。主视角决定整封信的理解，朋友身份负责怎样对“你”说话。
2. 回信允许最多 2 个辅助视角，其他主辅规则沿用共享协议。只在明确盲点时加入，不能因写信就默认凑齐。
3. 按 `references/friend-voice.md` 写完整初稿。人物的判断习惯要进入主要展开段落，而不只体现在开头、结尾或一句概括；不能把候选洞见摘要当作成品，也不能把不同视角统一成“承认困难—兼顾生活—保留未知”。
4. 单独审阅初稿：先做共享忠实度检查，留下简短的成品定位记录，再做下方回信质量门。人物路径缺失就重新理解，理解成立但回应不足才补写；两者均不能靠加风格词修复。摄取附带回信也须单独审阅，不能用其他页面完成或样式审计通过代替。独立版本执行相同审阅，但仍不读取旧信。
5. 正文末尾用 `## 依据` 集中列出来源；只有归档回信更新近况对话总览和日志。

## 正文要求

- 像一个了解你来路的朋友写给“你”，不是咨询报告、绩效复盘或思想讲义。
- 围绕一个中心洞见，至少落到两个有实质作用的具体细节或原句。可以省略无关枝节，但不能省略使这个中心成立的挣扎、矛盾和转变；两个细节是证据底线，不是写作完成标准。
- 让读者看见这份理解怎样从经历中长出来：哪些事让用户困住，哪些相互牵扯的感受或愿望仍然成立，哪一个细节让事情有了不同的看法，新的看法又保留了哪些难处。按来源实际包含的内容自然展开，不强造转变，也不把这些问题写成固定章节或每封必备的分析步骤。
- 旧线索只有在它改变对今天的理解时才进入正文，说明具体的延续或差异，不能用“你一直如此”替代核验。打动来自准确看见与有证据的新理解，不来自催泪措辞、拔高或替用户编造未说出的感受。
- 不奉承，也不以挑错证明诚实。未知保持未知，推断使用有边界的表达。
- 标题、章节、反方、风险段、行动清单和金句收尾都不是必选。
- 建议通常为 0-1 个。只有主视角的推理自然要求验证或行动时才给。
- 材料丰富、包含多层处境或重要转变时，正文通常以约 1000—1600 字作为展开参考（不含标题、元数据和依据），不是最低字数或硬性上限。用户明确要求短信、材料单薄或充分展开后确实自然简短时可以更短；不能靠重复、补故事或增加建议凑长度，也不能因没有硬性字数而默认写成几百字摘要。
- 主视角决定理解最终停在哪里，领域成文要求决定到那里是否已写充分。允许停在画面、感受、机制或诚实未知，但要让读者跟得上它的分量；刚命名一个感受或说出一句概括，不等于已到停止位置。
- 正文不放 Obsidian 链接；`## 依据` 中保留精确来源。

## 回信质量门

- 哪两个具体事实支撑中心理解？是否把推断写成事实？
- 能否指出正文哪一段提出了超出日记复述的新理解，以及哪几处原始细节支持它？把用户原话换一种温柔说法、重复“生活也值得珍惜”等熟悉道理，不算通过。
- 删去中心概括后，具体段落是否仍让人理解它为什么成立？若只剩情节摘要和安慰，补足细节之间的关系及其分量，不堆更多概括。
- 来源里的关键挣扎、矛盾或变化是否获得了回应？是否为了温柔而绕过了难受、愤怒、遗憾或仍未解决的问题？不得强制所有素材转向积极结局。
- 长度是否由材料和展开程度决定？丰富材料若只写成短摘要，不能以“克制”或“留白”为由放行；更长但没有新增理解也必须删改。
- 它听起来像朋友，还是像审计、咨询、老师批改或名人模仿？
- 是否给喜悦、难过、关系和不知道留下空间？
- 共享忠实度检查是否落实到正文的主要展开段落，而非只在末尾补上一句人物式判断？
- 用户会因为被看见和获得新理解而愿意重读吗？

## 验证和维护

- 修改人物库或推理规则后，先执行共享 `tests/cross-domain-regression.md` 的独立成文与事后对照，再执行 `tests/semantic-regression.md`。语义审阅与结构验证分别报告，不把文档存在当作行为已通过。
- 批量新写或重写后，可运行 `python3 knowledge-engine/skills/build/companion-reflection/scripts/audit_style_repetition.py --strict <本轮页面...>`。脚本只检查确定性模板痕迹，不能判断展开程度、洞见或是否打动用户，不能替代单独审稿。
- 更新 Markdown 后按根 `AGENTS.md` 运行标签、链接和 Skill 体系验证。

## 禁止事项

- 在本目录复制共享人物文件、维护固定人物名单或建立第二份人物索引。
- 人物换皮、圆桌平均和名人背书按共享协议检查，本层不另设人物规则。
- 把每个细节都变成机制、风险、成长任务或行动清单。
- 为了反奉承写得冷淡，或为了朋友感制造不存在的亲密。
