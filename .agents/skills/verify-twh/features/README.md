# verify-twh 功能地图

这个目录是验证用户可见行为的唯一来源。驱动应用之前先读这份索引，再读对应功能的文件。机器可读的映射在 `studio/verification/features.json`。

## 基线前置条件

- `pnpm twh launch --build` 在临时目录里启动一个匿名实例，打印 `origin`。
- `pnpm twh doctor` 报告实例来自哪个提交、构建是否比源码旧。提交对不上或构建旧了就重启实例。
- 绝不驱动不是这次验证启动的实例，尤其是操作者自己开着的开发服务。
- 实例里只有演示库（虚构人物阿宁、虚构账单和照片）。需要模型的功能（整理成日记、回信、预测、入梦）在这里只能验证到"没有模型时的提示"这一步。

## 驾驭约定

- 每个配方都从基线状态开始，除非它的前置条件另有说明。
- 用无障碍角色和名字定位，不用 CSS 选择器，不用 DOM 位置。
- 命令逐字照抄。带 `?` 的路由加引号，免得 shell 把它当通配符。
- 单步操作走 `pnpm twh drive --eval "<js>"`，整段旅程走 `pnpm twh drive --script <名字>`，浏览器操作之外的原生菜单和快捷键见各功能的 Gotchas。
- 改动数据后把数据恢复。清理实例时不删证据。

## 证明和跳过怎么报

- 既截动作，也截动作之后的状态，不只截最后一屏。
- 界面证明包括一张无障碍树快照（`pnpm twh evidence aria <名字>`）和一张截图（`pnpm twh evidence screenshot <名字>`）。
- 改了存储的，把写下去的值读回来当第二个证明。
- 每份证据记下功能 id 和走的入口。
- 某个入口到不了，报告时写上试过的命令和缺的前置条件。不要用另一个入口的通过来冒充。

## 功能文件的格式

每个文件一个 H1 和一段描述，然后恰好四个 H2，顺序固定：

1. `Sub-features`：短 id 加一句话。
2. `How to get to it (user POV)`：每个用户入口。
3. `Driving it with twh`：以 `Preconditions:` 开头，每条加粗的用户动作配一条确切命令和可观察结果。
4. `Gotchas`：会让验证白跑或失真的坑，包括已知过时的现成脚本。

地图里只写用户路径、稳定的定位方式、需要的状态、命令和可观察的证明，不写实现细节。`node studio/scripts/check-feature-map.mjs` 校验这个格式。

## 现成脚本的状态（2026-11-28 静态比对，未运行）

不少现成的 `verify-*.mjs` 找的按钮名或选择器已经和源码对不上，例如「整理并保存」已改名「整理成日记」，`verify-photo-library` 围绕已删除的组件写。逐条的差异记在对应功能的 Gotchas 里。旅程红了先分诊：是产品回归，还是脚本过时。脚本过时就修脚本，单独提交。 nightly 巡检会持续核对这部分。

## 功能

- [此刻](./capture.md)：随手记、整理成日记、只存原文、照片来源、语音。
- [值得聊聊](./questions.md)：话题卡片和"聊聊这个"。
- [生活记录](./sources.md)：来源目录树、文件浏览、阅读与编辑、文件菜单。
- [导入资料](./imports.md)：聊天记录、消费账单、照片。
- [搜索](./search.md)：搜索面板和"查看全部搜索结果"。
- [已有理解](./knowledge.md)：知识卡片、思维模型、理解总览。
- [洞察](./insights.md)：成长路线和自我理解。
- [时间线](./timeline.md)：人生阶段、阶段聚焦页。
- [近况回信](./letters.md)：阅读、人物视角、版本历史。
- [人物与关系](./relationships.md)：人物页和关系图谱。
- [预测自己](./predict-self.md)：扫描了解度、生成预测。
- [梦境](./dreams.md)：入梦点、推演、梦醒。
- [偏好设置](./preferences.md)：通用、AI、存储位置、应用更新。
- [隐私](./privacy.md)：隐私与数据使用。
- [知识库切换](./knowledge-bases.md)：新建、切换、删除。
- [对话与检查器](./inspector.md)：浮动对话面板、命令面板、分离窗口（桌面专属为主）。
